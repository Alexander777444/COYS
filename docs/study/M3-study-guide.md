### Created / deleted

No new server files: the composition root (`routes/index.js`) already built the controller in M2, so
M3 only extends the existing classes. Nothing deleted. (A scratch verification script lived outside
the repository and was deleted after use.)

### Key lines

- `projectBodySchema` — `.strict()`: `id`, `createdAt`, `updatedAt` or any typo is a 400.
- `projectBodySchema` — `z.url({ protocol: /^https?$/ }).max(2048)`: only http(s) links, max 2048 chars.
- `ProjectRepository.create` — `JSON.stringify(project.technologies)`: the inverse mapping of
  `toProject`; SQLite stores an array as JSON text.
- `ProjectRepository.create` — after the `INSERT`, `return this.findById(project.id)` so the response
  carries the DB-generated `created_at`/`updated_at`.
- `ProjectRepository.replace` — `updated_at = strftime('%Y-%m-%dT%H:%M:%fZ','now')` and
  `if (changes === 0) return null`: no extra `SELECT` is needed to know whether the id exists.
- `translateConstraint` — only `SQLITE_CONSTRAINT_UNIQUE` becomes `ConflictError`; every other DB
  error is rethrown so it ends as a 500.
- `ProjectService.create` — `crypto.randomUUID()`: the id is generated by the server, not the client.
- `ProjectController.create` — `res.status(201).location(`${req.baseUrl}/${project.id}`).json(project)`:
  `req.baseUrl` is `/api/v1/projects`, so the header is `/api/v1/projects/{id}`.
- `ProjectController.remove` — `res.status(204).end()`: status only, no body, no `Content-Type`.

## 3. How the pieces connect

```
POST /api/v1/projects
  authenticate (401) → validate body (400) → ProjectController.create
  → ProjectService.create(data)  [adds id = randomUUID()]
  → ProjectRepository.create()   [INSERT; UNIQUE → ConflictError 409]
  → findById()                   [row with DB timestamps]
  → 201 + Location: /api/v1/projects/{id} + JSON body

PUT /api/v1/projects/{id}
  authenticate (401) → validate params, then body (400) → controller.replace
  → service.replace(id, data)
  → repository.replace()  [UPDATE …; changes === 0 → null → service throws 404]
                          [UNIQUE violation → 409]
  → 200 JSON

DELETE /api/v1/projects/{id}
  authenticate (401) → validate params (400) → controller.remove
  → service.remove(id) → repository.deleteById() [false → 404]
  → 204, no body
```

Check order on every new endpoint: **authenticate → validate params → validate body → service**.
So no token + bad body = 401; bad body + missing id = 400; valid body + missing id = 404;
duplicate slug = 409 (only reached when the row/insert is actually valid).

## 4. Key ideas

1. **409 is decided by the database.** A "does this slug exist?" query in the service would be a race
   between two requests; the UNIQUE index is atomic, so the repository translates its error.
   *Analogy:* the door alarm fires, the guard does not guess who is inside.
2. **PUT replaces the whole form.** Omitted optional fields go back to their defaults; nothing is
   merged from the old row. *Analogy:* you hand in a new form, you do not edit the previous one.
3. **201 + `Location` is a receipt with an address.** The client learns where the new resource lives
   without searching for it. *Analogy:* a shop tells you the shelf number of what you just bought.

## 8. Three questions the professor could ask

1. **Why does the repository throw the 409 and not the service?**
   Uniqueness is enforced by the `UNIQUE` index at insert/update time. A "check then insert" in the
   service could pass the check and still fail under two concurrent requests. The repository
   translates the database error into `ConflictError`; the service stays free of SQL details.
2. **How does `PUT` know the project exists without a `SELECT` first?**
   `UPDATE … WHERE id = ?` reports `changes === 0` when no row matched, so the repository returns
   `null` and the service raises `NotFoundError`. One statement, no race between check and update.
3. **Why is the UUID generated in the service?**
   The id is server-owned (the client cannot choose it) and it must exist before the `INSERT`, so the
   response and the `Location` header can reference it. Generating it in the service keeps the
   repository a pure data mapper.
